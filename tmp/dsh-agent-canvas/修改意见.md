> 审查对象：`/tmp/acx` 迭代工作区、`/tmp/dsh-agent-canvas`（git 仓库）、`define_*.json` 载荷
> 结论先行：当前流程是「在 /tmp 里、对构建产物打字符串补丁、用正则自证、在假环境里测、且很可能没上线」。

## P0-0 先排掉"测的和跑的不是一份"这个不确定性

**为什么**：README 写明 `src/client.js` 就是 `cordis_define` 的 `code.client`，动态插件不落盘。
对账结果 `define_client.json`(18:42) 只有 patch23 标记，**没有 patch24**；而 `v21.client.js`(19:31) 两者都有。
如果最近一次 `cordis_define` 喂的是 `define_client.json`，性能面板/zoom/md 预览根本没进过 UI。

**动作**（任选其一，几分钟内可判定）：
1. 看 GUI 工具栏有没有「性能」「适应」两个按钮；没有 → 跑的是 patch24 之前的版本。
2. 直接查运行中 cordis package 的 `code.client` 内容，比对 `md5`。
3. 给 client 启动日志加一行源码指纹，例如：
   ```js
   console.log('[agent-canvas] build ' + BUILD_STAMP + ' bytes=' + CLIENT_LEN)
   ```
   以后每次 `cordis_run` 都能一眼确认版本。

> 未确认版本前，所有 gate / bench 结论都不可信。

## P0-1 建立单一真源 + 可复现构建

**现状**：真源被拆成三份——
- git 仓库 `dsh-agent-canvas/src/client.js` = 71 KB（初始提交 `7596ecf`，无 patch23/24）
- `/tmp/acx/v21.client.js` = 120 KB（全部成果，**未提交**）
- `/tmp/acx/define_client.json` = patch23 快照（**落后于 bundle**）

**动作**：
1. 回迁：以 `v21.client.js` / `v21.host.js` 为基线覆盖仓库 `src/`。
   ```bash
   cp /tmp/acx/v21.client.js /tmp/dsh-agent-canvas/src/client.js
   cp /tmp/acx/v21.host.js /tmp/dsh-agent-canvas/src/host.js
   cd /tmp/dsh-agent-canvas && git add -A && git commit -m "canvas: pkg23 perf fixes + pkg24 zoom/md/perf-hud"
   ```
2. **删掉第二个 clone** `/tmp/dsh-canvas`（与 `dsh-agent-canvas` 同源，已分叉隐患）。
3. 新增 `build.mjs`，把 `src/*.js` → `define_*.json` 变成一条命令：
   ```js
   // build.mjs — 读 src，产出 cordis_define 载荷，并在尾部写入指纹
   import fs from 'node:fs'
   import crypto from 'node:crypto'
   for (const kind of ['client', 'host']) {
     const src = fs.readFileSync(`src/${kind}.js`, 'utf8')
     const md5 = crypto.createHash('md5').update(src).digest('hex')
     fs.writeFileSync(`define_${kind}.json`,
       JSON.stringify({ code: src, md5, builtAt: new Date().toISOString() }, null, 2))
     console.log(kind, src.length, md5)
   }
   ```
4. `package.json` 加脚本：`build` / `gate` / `bench`；`define_*.json` 加入 `.gitignore`（它是产物）。
5. 仓库里保留一份 `CHANGELOG.md`，每个通过的 gate 对应一次 commit。

**目的**：以后复现只需 `npm run build`，而不是按顺序重放 `patch1..patch24c`。

## P1-1 修掉已知真 bug：moveRenders 计数器

**位置**：`v21.client.js:1046`，位于 `function CanvasApp() {` 渲染体开头：
```js
function CanvasApp() {
  if (PERF.moves > 0) PERF.moveRenders += 1   // ← 错
```
**问题**：只要发生过一次 move，**之后每次渲染都 +1**，统计的不是"由拖动触发的重渲染"，面板上这个指标是假的。
**改法**（快照比较，只在 move 数变化时计一次）：
```js
let perfLastMoves = 0            // 模块作用域
function CanvasApp() {
  if (PERF.moves !== perfLastMoves) {
    PERF.moveRenders += 1
    perfLastMoves = PERF.moves
  }
  const st = useStore()
  ...
```
**补测**：在 gate 里加一条**行为**断言（见 P1-4），而不是 grep `moveRenders` 字符串。

`gate21` 的 "measured culling" 量的是内联复制的 `vis()` 公式。数字反映的是重构出的假环境。

**动作**：

2. 在**真实 GUI 实例**里录 Chrome DevTools Performance：拖动一帧、缩放、打开会话列表，看长任务归属。
3. 复用已有的 `PERF.hostMs` / `PERF.drawMs`：在真实实例里按「性能」按钮读数，而不是 mock 里跑。
4. 先回答一个问题：**瓶颈是 canvas 绘制，还是 host 的 listSessions？** 再决定优化方向。

## P1-3 解决 390ms 的根因，而不是缓存掩盖

**现状**：`patch24a` 注释自认 `sessionQuery.listSessions()` ≈ 390 ms host CPU（全量读盘）。
`patch23` 的"修复"是 host 端缓存 10 s + 轮询放慢到 15 s——只降低触发频率，单次成本没变。

**动作**（按性价比排序）：
1. **增量**：记录每个会话文件的 `mtime`，只解析变化的文件。
2. **瘦身**：只读列表需要的字段，避免整份记录反序列化（看 `listSessions` 是否能带字段投影）。
3. **预热 + 事件驱动**：启动时建索引，之后由变更事件更新，轮询只做兜底。
4. 缓存 10 s / 15 s 轮询保留为最后一道防线，不作为主方案。

# 附：四点验收结果（对 `v21.client.js` 的行为核查）

> 方法：从 bundle 中**原样抽取**相关函数，在 Node 里执行真实调用（`/tmp/acx/check_features.cjs`），
> 而不是 grep 字符串。另配合逐行阅读调用链。

## ① 性能监测（找 where 卡）— ⚠️ 框架在，关键指标不可信

- ✅ 有 `PERF` + `perfFrame()` + 工具栏「性能」按钮 + HUD 面板；测「帧绘制 ms / 峰值 / FPS / 当帧节点数 / 拖动事件 / 触发重渲染 / Host 最慢往返」。
- ❌ **`moveRenders` 数错**：`v21.client.js:1063` 的 `if (PERF.moves > 0) PERF.moveRenders += 1` 在 `CanvasApp()` 渲染体内。只要有 ≥1 次 move，之后**每次渲染都 +1**，不是"该次 move 引发的渲染"。HUD 的"触发重渲染（目标 0）"失真。
- ❌ **没有 host 内部埋点**：只测 client 侧往返总时长，不分段 `listSessions` / `canvas-list-files` 各自耗时；而注释自认 `listSessions` ≈ 390 ms 才是主嫌疑。
- ❌ **不测 React 渲染耗时**，而"卡"很可能在渲染/host，不在 canvas draw。
- 修法：`moveRenders` 改快照比较 `if (PERF.moves !== perfLastMoves) { PERF.moveRenders += 1; perfLastMoves = PERF.moves }`；host 每个 handler 记 `durationMs` 回传，HUD 显示按方法的分解。

## ② 指定 .md 文件在 canvas 上显示内容 — ⚠️ 能显示但有 6–30s 延迟

- ✅ `isMarkdown` 识别 `.md`；`nodeH` 使节点高 118px；drawGraph 画 `mdLinesOf(f)` 前 6 行；host 有 `canvas-read-text`；`fetchMarkdown` 带缓存与并发上限（12）。
- ❌ **首屏延迟**：首次扫描时 `mdText=null`；异步返回后只写 `mdCache` 并 `store.set({})`，**没有把 text 写回 store 里当前的 file 对象**。节点一直显示"读取中…"，直到**下一次文件扫描**（6 s，慢走则 30 s）才显示。
- 修法：在 `.then` 里 `store.set({ files: store.get().files.map(...) })` 把 `mdText` 就地合并进去，或让 drawGraph 直接查 `mdCache[f.path]` 而不是 `f.mdText`。

## ③ 放大缩小 — ✅ 核心可用，`适应` 有缺陷

- ✅ `onGraphWheel`（滚轮 0.9/1.1，锚定光标）、`− / % / +`、`适应`、`clampZoom` 0.3–2.5、`zoomTo` 锚点公式正确、`fitToContent` 遍历所有节点。
- ⚠️ `fitToContent` 算出的缩放被 `clampZoom` 下限 **0.3** 钳死；内容远大于视口时，"适应"点完**仍装不下**，无法真正"看全"。
- 修法：fit 用更低下限（如 0.05），或允许 fit 结果低于手动缩放下限。

## ④ 按文件夹层级显示 — ❌ 未真正实现

实测（`check_features.cjs`，2 个同深度目录 a/、b/ 各 3 文件）：

```
a/f1.txt index=0 -> x=412 y=-30
a/f2.txt index=1 -> x=412 y=24
a/f3.txt index=2 -> x=412 y=78
b/g1.txt index=3 -> x=402 y=132
b/g2.txt index=4 -> x=402 y=186
b/g3.txt index=5 -> x=402 y=240
```

- ❌ `filePos` 的 `index` 来自 useMemo 的 **per-owner 扁平计数** `ownerSeen[agentId]`，不是按目录。结果：同深度不同目录的文件全部落在 **同一列**（仅 10px 抖动），y 按扁平序号连续递增 → **目录之间交错，没有分组行**。与注释"directory -> grouped rows / siblings cluster"不符。
- ❌ `assignOwner` 返回 null 的文件在 useMemo 里被放到固定 `{x:60,y:60}`，**所有未归属文件重叠在同一点**。
- 修法：按 `dirOfRel(rel)` 先分组，用**每个目录自己的行计数**决定 y；目录之间加分隔；无主文件按索引排开而不是固定点。
